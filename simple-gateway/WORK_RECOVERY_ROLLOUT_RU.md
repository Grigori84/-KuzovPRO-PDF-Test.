# Work: безопасное развёртывание recovery-кандидата и откат

11.11.2026. **Инструкция для будущих отдельно разрешённых действий. Ничего из
облачных шагов ниже Codex не выполнял.** До отдельного разрешения владельца
`POST /pdf` остаётся на `gateway-disabled`, функция приватная. Эта инструкция
не разрешает менять IAM, бакеты, ключи, allowlist или записи клиентов.

## 1. Зафиксировать исходное состояние, не изменяя его

1. В разрешённой Work-сессии прочитать и сохранить локально полную текущую
   спецификацию API Gateway, её revision/ID, backend/tag для `POST /pdf`, точную
   функцию и версии, на которые указывают теги. Исторически `gateway-disabled`
   указывал на `d4e4j49ue1g1m049iojs`; это **не** доказательство текущего значения.
   Проверить, что POST сейчас действительно возвращает 503 GATEWAY_DISABLED.
   Если маршрут уже иной — остановить изменение и сверить с владельцем.
2. Сохранить метаданные существующей функции: service account ID, entrypoint,
   runtime, memory/timeout, переменные и **ссылки** на secret bindings, ограничения
   вызова и доступные версии. Значения секретов не копировать в GitHub/чат/логи.
   Установить, какому исходнику соответствует реально работающий backend;
   серверный PR #1 сам по себе не доказывает состав живой версии.
3. Прочитать текущие Lifecycle/политики обоих существующих бакетов, наследуемые
   роли и allowlist без изменений. Проверить, что `control/` и новый
   `begin-requests/` не попадают под удаление, в том числе общее правило на весь
   бакет. Нельзя терять отображение request_id→ID или tombstone после 60 дней.
   Staging 1 день и публичные estimates 60 дней сохраняются. Если правила
   несовместимы — блокер до отдельного согласования, не исправлять молча.
4. Сохранить точный способ вернуть **исходную disabled-спецификацию** и контрольный
   hash файла в рабочем журнале Work. Не менять существующий disabled-тег и не
   использовать `$latest` для рабочего маршрута. Снимки без секретов/документов.

## 2. Получить проверенный пакет локально

В отдельном чистом checkout ветки `fix/pdf-gateway-recovery`:

```bash
cd simple-gateway
node --version                       # Node.js 22
npm ci --ignore-scripts --no-audit --no-fund
npm test                             # сейчас 73 pass, failures/skips 0
python3 scripts/build-release.py      # только локальный ZIP, не deployment
sha256sum build/*.zip
```

Проверить source_commit, runtime, зависимости и SHA в соседнем manifest; ZIP
должен содержать `index.js`, `workflow.js`, `ephemeral.js`, `selftest.js`,
`recovery-selftest.js`, `recovery-journal.js`, package/lock, `node_modules`, `RELEASE-MANIFEST.json`.
Текущий кодовый commit и воспроизводимый ZIP зафиксированы в
[RECOVERY_VALIDATION_RU.md](RECOVERY_VALIDATION_RU.md). Документационные коммиты
меняют source_commit/имя нового ZIP, это допустимо при повторной сборке/сверке.

Не собирать из нескольких PR, не править ZIP в консоли и не использовать
плавающий `npm install`. Не добавлять статические IAM/S3-ключи в архив.

## 3. После отдельного разрешения — приватная диагностика с durable run-id

**Уточнение 12.11.2026:** журналы Cloud Functions недоступны; доступ к Monium
для этой функции не доказан. Логи и ответ зависшего вызова не используются как
единственный реестр. Сейчас ничего не развёртывать и selftest не запускать:
порядок ниже применим только после отдельного разрешения владельца.

1. Создать новую приватную диагностическую версию **существующей** функции из
   нового ZIP с `recovery-journal.js`. Прежние account/secret bindings/два бакета
   сохранить. Node.js 22, `selftest.handler`, `SELFTEST_ENABLED=true`,
   `GATEWAY_ENABLED=false`, **`LEGACY_WRITERS_DRAINED=false`**. Для новой версии
   timeout 180с. Маршрут по-прежнему `gateway-disabled`; не направлять его на
   selftest, не менять IAM/бакеты/ключи. Старый ZIP d9cddbe не содержит реестра
   и для этой процедуры непригоден.
2. **До вызова** локально создать случайный run-id (32 hex) (например,
   `python3 -c 'import secrets; print(secrets.token_hex(16))'`), сохранить его в
   журнале Work вместе с точной version ID. Один run-id — один запуск; не терять
   и не заменять его при timeout. Вкладка Testing → No template/custom raw JSON;
   только прямой приватный IAM-вызов точной версии, без HTTP-обёртки:

   ```json
   {"operation":"recovery","action":"prepare","run_id":"<сохранённый32hex>"}
   ```

   Prepare сохраняет **весь** план пяти ID/request_id/токенов в закрытом бакете
   `selftest-runs/<run_id>.json` через If-None-Match, до любого begin/control,
   PUT/MPU. Здесь ещё нет тестовых control/PDF/MPU. Даже при потере ответа путь
   известен заранее; повтор prepare возвращает прежний план, не создаёт новые ID.
   Старые незарегистрированные команды upload/publish/revoke теперь отклоняются.
3. Прочитать `selftest-runs/<run_id>.json` через существующий Object Storage UI
   и сохранить список `rows[].id` в Work. Не выгружать секреты/клиентские файлы.
   Выполнить **read-only**:

   ```json
   {"operation":"recovery","action":"status","run_id":"<тот же32hex>"}
   ```

   Status возвращает все 5 ID, control phase/absent, наличие staging/public и
   список multipart UploadId **по точному ключу каждого ID**, включая поздние
   загрузки с потерянным ответом Create. Выдача PUT-ссылок при status отсутствует.
   Реестр не удалять/не подвергать Lifecycle; проверить существующие правила
   без их изменения. Для первого запуска phase=prepared и все объекты отсутствуют.
   **Стоп до run:** нельзя прочесть/проверить реестр, status/list вернул403/5xx,
   не совпал список ID, найдены чужие объекты или правило удаления selftest-runs.
   Не расширять права автоматически. Monium не нужен для продолжения, если
   эти существующие read-only пути работают; иначе диагностика заблокирована.
4. Только после успешного шага3:

   ```json
   {"operation":"recovery","action":"run","run_id":"<тот же32hex>"}
   ```

   CAS prepared→running разрешает **один** запуск. Повтор run после timeout
   запрещён409: дальше только status/cleanup того же run-id. Нет новых ID при
   повторе. Журнал намерений Create пишется до запроса; UploadId — до первого
   part/Complete. Ошибка/таймаут между control commit и возвратом ID не теряет ID:
   он уже был в плане. Status/cleanup работают без исходной памяти процесса.
5. Нормальный результат: HTTP200, `result:PASS`, все прежние checks
   (`lost_begin_same_id`, `lost_complete_response_recovered`, `revoke_tombstone`,
   `conditional_complete_no_overwrite`, `abort_complete_race_x3`,
   `late_complete_cannot_recreate`), `runtime:v22...`, SDK3.1166.0/pdf-lib1.17.1.
   Три флага true: known_uploads_fenced/public_absence_verified/tombstones_retained.
   Дополнительный status: phase=cleaned, все control=revoked, staging/public
   отсутствуют, upload_ids пусты. Uncached анонимный GET всех 5 публичных ключей
   →404. Сами control, begin mappings и selftest-runs сохраняются.
6. При зависании, timeout, потерянном ответе или любом FAIL: **не повторять run
   и не начинать другой run-id**, прочитать прежний реестр/status, затем:

   ```json
   {"operation":"recovery","action":"cleanup","run_id":"<тот же32hex>"}
   ```

   Cleanup CAS-переводит запуск в cleaning, запрещает его продолжение, для ещё
   не созданных control сохраняет tombstone штатным v2-отзывом. Поздний begin
   не создаст обходной ID. Известные/однозначно найденные MPU требуют подтверждённый
   Abort+ListParts/NoSuchUpload перед удалением принадлежащего тесту PDF.
   Отложенный Complete не получает разрешения на повторную запись. При потере
   ответа cleanup повторять **cleanup того же run-id**, не править JSON вручную.
7. **Точные стоп-условия восстановления:** SELFTEST_PENDING_IO_RECHECK означает,
   что Create/PUT ещё мог не завершиться; отсутствие объекта само по себе не
   доказывает завершение. Не считать CLEANED/PASS, оставить cleaning/route disabled.
   После фактического завершения запроса повторить status/cleanup: пустой MPU
   находится по запланированному точному ключу, завершившийся staging PUT — по
   реальным байтам/SHA. Если pending не разрешается или исход нельзя установить,
   остановиться и запросить поддержку; таймер не снимает барьер. Неизвестный
   дополнительный upload, чужой control/PDF, неподтверждённый Abort, ошибки CAS,
   403/5xx — также стоп; никакой массовой очистки или IAM-изменений. Каждый ключ
   остаётся учтённым в сохранённом реестре, даже если запрос завершится позднее.
8. CLEANED означает очистку, **не успешность прерванных contract-checks**. После
   анализа причины новый проверочный запуск допустим только с новым заранее
   сохранённым run-id и согласованным объёмом. Живые проверки должны подтвердить
   реальный conditional Complete и терминальный Abort при гонках; три опыта не
   заменяют контракт/ответ поддержки провайдера. До этого никакой активации.
9. После испытания обычная приватная версия того же ZIP: `index.handler`,
   SELFTEST_ENABLED=false/GATEWAY_ENABLED=false. Ни diagnostic entrypoint, ни
   новый рабочий тег сейчас не направлять в API Gateway.

## 4. Старые control v1: отдельный обязательный барьер

Raw PutObject старой функции нельзя отменить через новый multipart UploadId.
Поэтому `LEGACY_WRITERS_DRAINED` по умолчанию false. Возраст записи, 409, HEAD 404
и клиентский timeout **не** доказывают завершение прежней записи.

До разрешения миграции v1 Work должен доказать отсутствие старого ingress,
других triggers/ручных вызовов и всех старых выполняющихся invocations, а также
терминальное завершение отправленных ими S3 PUT/SDK-повторов. Нужны сведения
логов/провайдера об исходе запросов; простого «подождали N минут» недостаточно.
Если доказать нельзя — оставить flag false и шлюз disabled, сообщить блокер
**миграции v1**. Это не запрещает новую приватную диагностику/публикации v2:
они работают при false без миграции v1. Не поднимать флаг ради selftest.

Только после доказанного drain и отдельного разрешения создать следующую версию
с `LEGACY_WRITERS_DRAINED=true`. Флаг задаёт оператор на сервере, не клиент.
В самой миграции новый код читает control/ETag и реальные байты объекта:

| Состояние v1 | Действие нового кода после drain |
| --- | --- |
| publishing + точный PDF | CAS в v2/published; затем штатный revoke при необходимости |
| publishing + объекта нет | CAS в v2/issued, SHA сохраняется; тот же ID публикуется при наличии staging либо отзывается |
| несовпадающий объект | 409, ничего не перезаписывать/не удалять |
| уже published | повтор publish подтверждает объект без мутации; revoke требует drain |

**Не редактировать реальные control JSON вручную, не удалять их, не сбрасывать
publishing по таймеру, не выдавать новый ID вместо зависшего.** Операции с
существующими клиентскими записями требуют отдельного разрешения владельца.
Не пытаться «найти» старый lost begin по совпадению суммы/MD5: два намеренно
созданных документа могут совпадать. Операция Android 22 без ключа — ручная сверка
по устройству/времени с сохранением исходных записей, не автоматическая замена.

## 5. Клиент и отдельное разрешение активации

- Сервер совместим с установленной Android **1.1.1/code 22** по прежним begin,
  publish и revoke. Автовосстановление lost begin возможно только для новых
  операций Android **1.1.2/code 23** из отдельного PR `fix/kuzovpro-begin-recovery`
  в [Grigori84/KuzovPRO PR #40](https://github.com/Grigori84/KuzovPRO/pull/40). Сборка/подпись — по его инструкции Codemagic112.
  Установка здесь не выполнялась. Старый BEGIN_UNKNOWN без ключа не становится
  восстановимым после обновления; не очищать данные/журнал ради обхода.
- Пройти Android/Compose тесты на Linux/KVM и проверить signed update 23>22 с
  прежним сертификатом/applicationId. Копию/restore проверять на отдельном
  экземпляре. Уже подтверждённый владельцем update22/data preservation и старый
  полный Samsung happy-path без причины повторять не нужно.
- После частной диагностики, решения по legacy и отдельного разрешения владельца
  создать production-версию `index.handler`, `SELFTEST_ENABLED=false`,
  `GATEWAY_ENABLED=true`, с тем же ZIP и согласованным legacy flag. Закрепить
  новый рабочий тег, например `gateway-recovery-v2`, за **конкретной версией**.
  Записать version ID, ZIP SHA, env/binding references и hash спецификации.
  Старый `gateway-disabled` не перепривязывать; `$latest` не использовать.
- Только при отдельно разрешённом окне переключить POST/pdf на этот рабочий тег.
  Провести короткую **новую проверку отказа** на искусственной смете: потерять
  ответ begin_v2, закрыть/открыть клиент, повторить Отправить, сверить прежний
  recovery code→тот же ID и ровно один публичный PDF; проверить отзыв после
  неоднозначного publish. Использовать заранее подготовленный локальный сетевой
  fault harness, не менять TLS/ключи и не обрывать случайно реальные запросы.
  Закончить подтверждённым отзывом/404. Подтвердить готовую SMS и фактическую
  доставку согласованному тестовому адресату — отправляет сам мастер.
- Для двух реальных мастеров нужны два зарегистрированных рабочих ключа.
  По прежнему аудиту есть Samsung владельца и отдельный тестовый клиент 0.2;
  это не два мастера. Регистрация напарника — отдельное разрешение, без общей
  регистрации/синхронизации. Тестовая изоляция двух ключей уже покрыта offline.
- До эксплуатации остаются согласование хранения/Lifecycle/nonce cleanup,
  допустимых расходов/лимитов/уведомлений и процедуры при потере телефона/Keystore.
  Эти настройки не изменять в рамках данного исправления.

## 6. Откат и аварийное выключение

Триггеры: повторный ID для одного request_id, воскресший PDF, object conflict,
неподтверждённый Abort, ошибки auth/реальных PDF, рост 5xx, утрата данных.

1. В разрешённой аварийной процедуре восстановить **точную сохранённую
   disabled-спецификацию** (POST→прежний gateway-disabled), перечитать её и получить
   503 GATEWAY_DISABLED. Зафиксировать время/активные invocations; отключение
   ingress не останавливает уже начатые вызовы и не отзывает публичные PDF.
2. Сохранить v2 control, begin-requests, nonce, writer UploadId и tombstone;
   не восстанавливать старые JSON поверх новых и не стирать их для совместимости.
   Новое Android-приложение хранит тот же request_id после 503/старого backend.
3. Для возврата функции выбрать последнюю **совместимую v2** проверенную версию
   после анализа причины. Если такой нет, оставить gateway-disabled.
   Старую raw-PUT версию **не включать над данными v2**: она не умеет fencing,
   а её проверка версии control специально откажет в доступе к v2. Откат на
   старый работающий v1 backend не является безопасным штатным rollback.
4. Убрать diagnostic entrypoint/SELFTEST_ENABLED из любых обслуживающих маршрут
   версий. Не менять service account/IAM/ключи/бакеты в попытке исправить откат.
5. Отдельно обработать находившиеся в полёте операции/отзыв только новым
   совместимым кодом после проверки фактического состояния. Сохранить исходные
   артефакты и безопасные коды ошибок; не заявлять об успешном отзыве на одном 503.

В рабочем журнале Work итог должен содержать: исходный/итоговый маршрут и
version IDs, source_commit/ZIP SHA, entrypoint/flags без секретов, результат
частных contract-checks и synthetic cleanup, доказательство legacy drain либо
его блокер, версию/сертификат клиента и фактические новые device-проверки,
результат проверки rollback. Автотесты сами по себе эксплуатацию не принимают.
