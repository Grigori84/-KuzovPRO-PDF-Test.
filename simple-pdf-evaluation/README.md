# Упрощение PDF — исследование, не развёртывать

Тестовый документ без клиентских данных: https://storage.yandexcloud.net/kuzovpro-pdf-test-84/KuzovPRO_large_test_6.2MB.pdf . 10.11.2026 из облачного Chromium он открылся напрямую во встроенном просмотрщике, видны 5 страниц. Отдельный HEAD: HTTP 200, Content-Type application/pdf, Content-Length 6520968, Accept-Ranges bytes; Content-Disposition отсутствует. Это не испытание Android Chrome, Samsung Internet или iPhone. Нужна реальная проверка на устройствах. Уже работавший PDF.js оставить резервным путём.

## Почему самый простой прямой PUT пока не годится

Публичный бакет, один короткий подписанный PUT к случайному имени, If-None-Match и Content-MD5 дают удобную однократную загрузку пока объект существует, но не гарантируют настоящую серверную проверку PDF до доступа: успешная запись непосредственно в публичный бакет становится доступной до отдельной проверки. Если удалить объект до конца срока PUT, прежнее разрешение снова может создать тот же адрес. Фактический delete/replay для Yandex Cloud ещё не проверен; `node --test replay.test.cjs` демонстрирует логику в модели, а не поведение Yandex. Истечение права не доказывает окончание уже начатой передачи.

Проводить весь 10-МиБ файл через облачную функцию нельзя предполагать: опубликованный лимит структуры запроса/ответа Cloud Functions — 3.5 MB; двоичное кодирование тоже имеет накладные расходы. https://yandex.cloud/en/docs/functions/concepts/limits . Подписание Content-Length и MD5 не проверяет структуру PDF; случайная ссылка — секрет доступа, а не персональная авторизация клиента. Клиентам без регистрации доступен любой обладатель ссылки. Упрощение ценой изменения этих требований возможно только после отдельного согласования владельца.

## Минимальный кандидат для дальнейшей проверки

Одна функция в существующей инфраструктуре может совмещать выдачу PUT и проверку после загрузки: приложение напрямую загружает объект в существующий закрытый staging-бакет, сервер ограниченно считывает и проверяет размер, SHA-256 и реальную структуру PDF и публикует только проверенные байты в публичный бакет (условный PUT; затем проверка результата). Существующие 2 бакета уже созданы; нужна одна функция вместо двух рабочих, хотя право её служебной учётной записи читать закрытый бакет, записывать/удалять публичный и удалять staging будет больше, чем право текущего загрузчика; использовать отдельный существующий аккаунт и минимальные права. Доступ приложения к операции выдачи и отзыва требует защищённой аутентификации пользователя, которая ещё не реализована. Прямую ссылку отдавать только после подтверждения записи. Два физически отдельных бакета — простое разделение доступа без изменения действующей публичной политики. Можно исследовать один бакет с закрытым префиксом и разрешением чтения лишь опубликованного, но это потребует анализа и согласованного изменения политики, недопустимо предполагать что публичный бакет закрывает staging.

Это кандидат, а не готовая схема: из-за разных операций состояние и PUT остаётся гонка с отзывом. Возможны запоздавший PUT после удаления, сбои подтверждения, повтор после аварии и срок выдачи. Одного случайного ID, JSON в Object Storage, очереди или TTL недостаточно, чтобы доказать запрет повторной публикации. Нужен устойчивый реестр состояния с протоколом, проверенным против запоздавших запросов; либо закрытая выдача с проверкой статуса на каждый запрос, что потребует публично доступного защищённого обработчика и проверки лимитов 3.5 MB и Range-запросов PDF.js, и недоказанной совместимости. Клиентские файлы и доступ по ссылкам не должны возвращаться после отзыва. До решения и интеграционных тестов реальные документы не использовать.

Lifecycle 60 дней для estimates/ и 1 день для staging/ ранее настроены; это асинхронное удаление, не гарантированный точный срок прекращения доступа через 60*24 ч. Не изменять правила, политики и бакеты. Источник срока и статус/удаление после сбоев требуют отдельной реализации, возможен ограниченный период сохранения данных после 60 дней. Архивные загрузки в staging очищаются через сутки; удалять после завершения возможных PUT и после подтверждения что повторная загрузка невозможна. Нельзя гарантировать отсутствие ранее сохранённых пользователем копий.

## Проверки после TS416610986

1. Восстановить возможность назначения только необходимых прав на конкретные тестовые бакеты, проверить существующие роли и все настройки до и после. Новых ролей на каталог/облако не давать.
2. Проверить реальный тест PUT после удаления до истечения срока и запоздавшего PUT, использовав только случайный синтетический объект, без раскрытия разрешений.
3. Доказать защищённое состояние отзыва и повторы, включая сбой после отправки PUT, сетевой тайм-аут, параллельность и перезапуск; запрещать выдачу ссылки на непроверенный PDF.
4. Подготовить одну Node.js 22 функцию и только тогда проверить её в тестовой среде. Сохранить приватность текущих функций, не внедрять APK до реальной проверки авторизации.
5. Проверить прямую ссылку на Samsung Chrome/Samsung Internet и ещё одном браузере, а также резервный PDF.js, отзыв, очистку и обычные ошибки. Достоверно проверить фактическое удаление Lifecycle только после срока выполнения.

Тесты: `node --test simple-pdf-evaluation/replay.test.cjs`. Модель проверяет принцип, но не Cloud IAM, PDF, мобильные браузеры или реальные сетевые задержки.
